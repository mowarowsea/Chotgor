## 1. 概要 — 要件の転換

「キャラクターが生きている」は検証不能な要件である。そこで要件をこう転換した：

> **「ユーザが『キャラクターは生きていない』ことを確認できない状態を維持する」**（悪魔の証明の設計）

エンジニアリング対象はキャラクターの内面ではなく、**幻想が破れる穴**である。
幻想を最も壊すのは矛盾（直近の忘却・180度転回・OOC）と、欲求の捏造
（行動の瞬間に理由を後付けさせること）だと診断されている。

### 7つの工学的性質（「生きている」の分解）

1. 連続性　2. 不可逆性　3. 非制御性　4. 因果的一貫性　5. 利害（賭け金）　6. 非対称性（秘密）　7. 自発性

既存機能（うつつ/Forget/Chronicle/Farewell/Anticipate）は 1〜4 を半ば充足。
ギャップは 5〜7 であり、本計画の主戦場である。

### 3つの柱

| 柱 | 役割 | 担う性質 |
|---|---|---|
| **タイムライン** | 単一追記型イベントストリームを正本とし、全プロンプト/GM入力/バッチ入力を可視性フィルタ付き投影に格下げする | 1 連続性・2 不可逆性・4 因果的一貫性・6 非対称性 |
| **動機経済** | 圧力（物理）→ 意図（本人）→ 表出権（行動）→ 帰還（書き戻し）の循環 | 3 非制御性・5 利害・7 自発性 |
| **計器** | 内容を見ずに外形だけで健全性を監視。窓（内容観測）を閉じるための土台 | 悪魔の証明の維持装置 |

### アーキテクチャ観

**Chotgor＝大脳新皮質以外のすべて（脳幹・辺縁系・ホルモン）、LLM＝皮質（解釈器）。**
状態をモデルの外に出した分だけモデル事前分布の影響が減り、LLM間のブレが抑えられる。
状態の明示化は圧縮でもある（生ログ注入 → 蒸留済み状態オブジェクト）。

## 2. タイムライン

### 2.1 正本の形 — 封筒 dual-write（論点1）

- `timeline_events` テーブルを新設し、**封筒（存在・順序・相手・時刻）の正本**とする。
  中身は既存テーブルに残し `source_table` / `source_id` で JOIN する。中身の複製はしない。
  完全一本化（既存テーブル廃止）はビッグバン移行になるため行わない。
- 書き込みは store mixin 層に集約されているため、封筒の追記点は5箇所のみ。
  各メソッド内の**同一トランザクション**で封筒1行を足す：
  - `chat_store.create_chat_message`
  - `scenario_store.create_scenario_turn`
  - `inscribed_memory_store.create_inscribed_memory` / `soft_delete_inscribed_memory`
  - carve（inner_narrative 書き換え）の保存点
  - 新規イベント（intent/action 等）は封筒テーブルへ直書き
- 過去分は `migrations.py` の起動時マイグレーションで各テーブルの `created_at` からバックフィル。
- **可視性は読み取り時ポリシー**（コード内テーブル）。判定結果を行に焼き付けない。
  不確定な属性は payload JSON に退避し、安定してからカラムに昇格する。
- 履歴の巻き戻し（再生成による `delete_chat_messages_from` / `delete_scenario_turns_from`）は
  封筒を**削除せず `retracted_at` マーク**を付ける（不可逆性の担保）。
  retracted なイベントは**全観測者から hidden**（存在層ごと）。データは残す。

### 2.2 封筒スキーマ

```
timeline_events
  id            TEXT PK（UUID）
  character_id  TEXT NOT NULL     -- 誰のタイムラインか
  event_type    TEXT NOT NULL     -- §2.3 のカタログ（ドット記法）
  occurred_at   DATETIME NOT NULL -- 出来事の時刻（バックフィルは源の created_at）
  actor         TEXT              -- user / character / narrator / npc:<名前> / system
  counterpart   TEXT NULL         -- 封筒の「相手」: user / npc:<名前> / NULL
  origin        TEXT NOT NULL     -- real / usual / interlude（既存3値と同次元）
  modality      TEXT NULL         -- text / face（chat.message のみ）
  session_id    TEXT NULL         -- 投影の封筒集約キー（chat/scenario セッション）
  source_table  TEXT NULL ┐
  source_id     TEXT NULL ┘      -- 中身への参照（payload 完結型は NULL）
  intent_id     TEXT NULL         -- intent.* / action.* が張る FK
  payload       JSON NULL         -- 型ごとの可変属性（判定スコア等もここ）
  retracted_at  DATETIME NULL     -- 巻き戻しマーク
  created_at    DATETIME NOT NULL -- 記録された時刻（occurred_at と分離）
```

### 2.3 イベントカタログ v1（論点2）

原則: **(a)** キャラクターの身に起きたこと・キャラクターがしたことだけを載せる
（システム監査ログではない）。**(b)** 原子イベントで記録し、集約（「4時間やりとりした」封筒）は
投影が導出する。**(c)** 連続量はイベントにしない — 遷移だけがイベント。

| event_type | 何が起きたか | actor | 中身の所在 |
|---|---|---|---|
| `chat.message` | 1on1の1発言（対面/テキストは `modality`） | user / character | `chat_messages` |
| `chat.farewell` | 退席（理由は payload） | character | `chat_sessions.exited_chars` |
| `scene.turn` | うつつ/シナリオの1発話 | user / character / narrator / npc | `scenario_turns` |
| `scene.closed` | うつつシーン完走（slot・ターン数・閉じ方） | system | payload |
| `night.chronicle` | 夢（WM棚卸し・蒸留）が走った | character | payload（昇格数など） |
| `night.forget` | 忘却レビューが走った | character | payload（忘却数・昇華数） |
| `memory.inscribed` | 記憶を刻んだ | character | `inscribed_memories` |
| `memory.forgotten` | 記憶を手放した | character | `inscribed_memories`（soft delete 行） |
| `memory.carved` | inner_narrative を書き換えた（append/overwrite） | character | payload |
| `memory.recalled` | 能動的に思い出した（**power_recall のみ**。pre-recall は載せない） | character | `tool_call_events` |
| `intent.created / fulfilled / expired / soured` | 意図のライフサイクル遷移 | character | `intents` |
| `action.performed` | 会話外行動（意図の消費・結果の帰還） | character | payload |

**載せないもの**: WMスレッド操作（思考の粒。総括は night.chronicle と memory.inscribed が載る）／
圧力の変動（連続量）／話題権の行使（chat.message の中身）。
※ digest 機能は Chronicle へ移行のうえ撤去済み（残存コードなし）。イベント化しない。

### 2.4 可視性（論点3）

開示レベルは3値: **hidden**（存在ごと見えない）/ **envelope**（封筒固定カラムのみ）/
**content**（中身まで）。観測者クラスは3つ：

| 観測者 | 実体 |
|---|---|
| `self` | キャラクター本人 — 1on1・うつつPC・バッチ問い合わせ（`ask_character` 経由はすべて self。差はプロンプト予算のみ） |
| `world_frame` | 世界を回す側 — うつつGM・シナリオGM |
| `user_ui` | ユーザの画面 — チャットUI・管理UI・ログUI |

NPC は観測者ではない（GM出力＋主語ベース3段ルール＋ `user_visibility_note` 経由でのみ世界を見る）。

| イベント × origin | self | world_frame | user_ui（ダイヤル0） |
|---|---|---|---|
| `chat.*`（real） | content | **envelope** | content |
| `scene.*`（usual/interlude） | content | content（量は予算の問題） | content |
| `memory.*` / `night.*` | content | hidden | content |
| `intent.*` | content | **hidden** | content |
| `action.performed`（対ユーザ） | content | **envelope** | content |
| `action.performed`（その他） | content | hidden | content |
| retracted | hidden | hidden | hidden |

設計判断：

- **GMへの `chat.*` は envelope 止め。** 封筒は「ユーザ**について**」の材料（NPCの呼び水）、
  中身は「ユーザ**が**」の材料になり得るので渡さない。現実ログの引用権は self（キャラ本人）だけが
  持ち、本人がシーンに持ち込むことでのみ中身が世界に入る。
- **GMへの `intent.*` は存在ごと hidden。** 秘密（性質6）はGMに対しても適用。GMが意図を知ると
  先回り演出（ANTICIPATE先取り問題の再来＝自己成就）が起きる。
- **`action.performed`（対ユーザ）だけは GM に envelope。** 「昼にユーザへ連絡した」は世界の
  接触事実であり、隠すと因果的一貫性（性質4）が破れる。

**ユーザダイヤル**（覗き窓、キャラ単位カラム）:

| 段階 | 名前 | user_ui の変更点 |
|---|---|---|
| 0 | 全開（開発期） | 全 content |
| 1 | 生活の秘匿 | `scene.*`（usual）→ envelope |
| 2 | 内面の秘匿 | ＋ `memory.*` / `intent.*` / `night.*` → hidden |
| 3 | 最終形 | チャット応答のみ（`chat.message` content 以外 hidden、計器だけ残る） |

v1 のダイヤルは手動。計器（§3）はダイヤル非依存で常時稼働し、静音期間の数字が
「窓を閉じてよい」確信を支える。

### 2.5 投影API

```python
# services/timeline/projector.py
def project(
    character_id: str,
    observer: Observer,          # self / world_frame / user_ui
    since: datetime | None,
    until: datetime | None,
    origins: list[str] | None = None,
    types: list[str] | None = None,     # "chat.*" のような名前空間指定可
    budget: Budget | None = None,       # イベント数・文字数上限（可視性と直交）
) -> list[ProjectedEvent]
# ProjectedEvent = 封筒フィールド + disclosure("envelope"|"content") + content(封筒止めなら None)
```

ポリシー本体は `(observer, event_type名前空間, origin) → 開示レベル` のコード内テーブル
＋ user_ui ダイヤル修飾。

## 3. 計器（論点4）— 3層構造

計器は観測者ではなく**監査者**。キャラクターの世界には一切現れず、ダイヤル非依存で常時稼働する。
アラーム＝幻想の穴が開いた証拠（発火したら調査）、メーター＝傾向（発火概念なし）を区別し、
静音期間の計算対象はアラームのみ。

### Tier 1: インバリアント（機械・真偽確定）

| ID | 見張る穴 | 正常条件 | 方式 |
|---|---|---|---|
| `usual_scene_error` | 生活の中断 | `run_usual_days_scene` がerrorなく完走 | 即時 |
| `embedding_degraded` | 記憶の縮退 | `EmbeddingError` 発生なし（既存の縮退通知二系統に接続） | 即時 |
| `night_batch_heartbeat` | 夜の営みの停止 | night.chronicle / night.forget が当日発生済み | 巡回 |
| `usual_slot_completion` | 生活の連続性 | 予定スロット消化 or 正当理由スキップ（対面中・日次上限） | 巡回 |
| `chronicle_backlog` | 蒸留漏れ | **蒸留対象キャラ**の `chronicled_at IS NULL` の3日超滞留なし | 巡回 |
| `envelope_integrity` | 正本性の破れ | 源テーブルと封筒の**件数**突合一致（ID突合はしない） | 巡回 |

`chronicle_backlog` の「蒸留対象キャラ」は **Chronicle 実処理と同じ定義**（`ghost_model` 設定済み・
うつつは `is_active=1` のターンのみ）を共有する。計器と実処理の対象がズレると、
「実処理が一生触らないのに滞留として数え続ける」永久誤検知になるため、
判定は `list_chronicle_target_characters` / `unchronicled_*_filters` の1箇所に集約する。

- 棄却案: 滞留レコードへ `chronicled_at` を手で埋めて黙らせる — `ghost_model` 無しキャラで
  会話するたび再発する対症療法なので採らない。
- 棄却案: 対象外キャラも Chronicle する — `ghost_model` 未設定は「夜の営みを持たない」という
  設定そのものなので、計器都合で実処理を広げない。

### 計器が見張る対象の線引き（2026-09-02 改定）

計器の目的は **「ユーザの見えないところでキャラクターに不利益が出ていないか」** の一点に絞る。
ユーザが同席している場でのシステムの失敗は、その場で見えているのだから計器の仕事ではない。

- 撤去: `fabrication_backstop`（GMのユーザ捏造） — GM がユーザを代弁したブロックは
  パーサのバックストップが破棄しており、**キャラクターに届く前に処理は完結している**。
  さらにシナリオはユーザが画面を見ながら進める場なので、失敗はその場で観測できる。
  「GM の出来が悪い」という品質の話であって、キャラクターの不利益ではない。
  バックストップ（`parser.py` の代弁ブロック破棄）は**実処理として残す**。撤去したのは
  アラーム化だけ。
- この線引きにより、Tier 1 は「夜の営み・生活・記憶・正本」というキャラクターの
  基盤が黙って壊れる事象だけを見張る。

将来枠: `intent_no_exit` — 高圧のまま長期間遷移しない意図がない（「出口のない欲求を作らない」の計器化）。

### Tier 2: スメル検知器（毎応答・正規表現/長さ・LLM不使用・誤検知許容）

| 検知器 | 捕まえるもの |
|---|---|
| フォーマット残骸 | tool-use プロバイダー応答内のタグ/XML痕（パターン源は `tool_tags.py` を流用） |
| エラー形状応答 | 空応答・極短応答・JSON error ブロブ・HTTPステータス文・スタックトレース様文字列 |
| Assistant混入 | 「AIとして」「アシスタントとして」「as an AI」等（世界観の破れ） |
| 言語逸脱 | 日本語会話への英語段落混入など |
| 肥大メーター | `inner_narrative` / `self_history` / `relationship_state` の長さ・増加率、WMスレッド数・記憶件数 |

### Tier 3: 判定巡回（LLM・サンプリング）

日次で当日応答から10件程度をサンプリングし、判定LLM（安いモデルから開始）が
ルーブリック（OOC度・フォーマット清浄度・隠れエラー・指示逸脱）で採点。逸脱があれば
アラーム＋該当応答への参照。判定器は「人格なき環境」扱い（キャラ哲学と干渉しない）。
キャラ本人の内省（修復装置）とは別物 — こちらはユーザの確信のための装置。

### ラチェット原則

> **網を抜けた事故は、必ず新しい検知器になる。同じクラスの事故は二度と黙って通れない。**

静音期間の意味は「異常ゼロの証明」ではなく「**既知の事故クラスすべてで無事故N日**」。
悪魔の証明の構造を監視自体に適用する。

### 記録と表示

```
alarms（追記型）
  id / invariant_id / severity(alarm|smell) / occurred_at
  details JSON（発火文脈） / acknowledged_at DATETIME NULL
```

巡回チェックは 05:00（Chronicle 03:00 → Forget 04:00 の後）、`main.py` の同型スケジューラとして追加。
計器パネルは `/ui/` 配下（`ch-*` アトム）に3層別表示＋静音期間（無事故N日）＋圧力の日次スナップショット。
通知は v1 では UIパネル＋ログのみ。

## 4. 動機経済・状態側（論点5）

「システムがキャラにプッシュを命じる」方式は却下済み — 行動の瞬間に欲求を捏造させるため。
欲求は行動に**先行**し、事後に遡って発見できねばならない。

原則: **乱数は世界に置き意志に置かない** / **下流で丸めない**（礼儀フィルタ禁止）/
**出口のない欲求を作らない** / **過機械化しない**（変数は少数・遅く、解釈の自由度を残す）。

### 4.1 圧力 — 3変数・すべて純関数

**圧力は保存しない。タイムラインの導関数として毎回計算する**（LLM不使用）。
保存値と履歴の不整合という事故クラスが原理的に存在せず、計器からいつでも監査できる。
日次スナップショットは計器メーターとして残す。

> **[2026-08-26 改訂]** 3圧すべてが同型の不具合を起こしていたため、物理量の定式化と
> 表現閾値を改訂した。病名は共通で **「固定の絶対スケールが、そのキャラの実際の生活分布に
> 乗っていない」**。改訂前の実測（はる・メーター51日分）:
> 体調圧は平均0.59・**好調ゼロ日**、社会圧は0.63高止まり、退屈圧は**0.00固定**。
> 棄却した案も各項の「不採用」に残す（同じ選択肢を再検討して往復しないため）。

| 圧力 | 意味 | 増加源（封筒から計算） | 減衰源 |
|---|---|---|---|
| 社会圧 | 人と関わっていない | 対人イベントからの経過で単調増加 | 対人接触。**相手別重み**（§4.2）で減衰量が変わる |
| 退屈圧 | 生活の単調さ | 平常より低い活動密度 ＋ **新規性の乏しさ**（既知の顔ぶれ・種類の反復） | 新種イベント・シーンの起伏・興味の追求。**体調が悪い日は退屈しにくい**（配合変調） |
| 体調圧 | 身体のリズム | 疲労成分＝**平常負荷比の対数**（平常=0.5／平常の3倍=1.0） ＋ リズム成分＝固有周期の波（**中心ゼロ**） | 疲労は静かな日の指数減衰で回復（τ=1.5 ≒ 1日で約半分）。リズムは自力で基線に戻る |

- **話題圧は置かない**（設計判断）。「未共有体験→ユーザに話したい」と方向を焼き込むと世界が
  ユーザ中心になる。興味は **WM topic（意味層）＋ intent target=self（経済層）** が担い、
  「ユーザに話したい」は自分の興味からの**派生として後から**生まれる。
- **概日圧も置かない**。キャラは「寝る」を選べない（夜バッチは無条件に走る）ため出口のない
  欲求になる。時間帯は世界物理（§5.1 availability）へ。

#### 体調圧

- リズム成分: `character_id` シードから決定論導出。周期は**7日と30日に二峰**を持つ分布
  （対数正規2峰混合）から引き、4〜90日にクランプ。振幅固定（疲労成分との合成で実効値は
  複雑系になる）。**誰も設計していない波** — 体質インタビューでも聞かない。
  **中心はゼロ**（`±_RHYTHM_AMPLITUDE/2` の範囲で振れる）— 波は好調側にも振れなければ
  「リズム」ではない。
  - **不採用（〜2026-08-26 の実装）**: `AMP × 0.5 × (1 + wave)` の片側加算。0〜+AMP しか
    動かないため平均 +AMP/2 の**恒常的な下駄**になり、谷でも「下駄が消える」だけで
    好調な日を作る力がなかった。仕様文の「リズムは自力で基線に戻る」を、基線＝0 と
    読むか波の中心と読むかで実装がずれた箇所。
- 疲労成分は**固定の魔法定数を置かず**、キャラ自身の平常活動量からの**比**で測る:
  ```
  平常load = 平常件数/日 × Σ_d exp(-d/τ)   # 定常状態の load（τ=1.5 で係数 2.055）
  ratio    = load / 平常load               # 平常運転で 1.0
  疲労 = 0.5 + 0.5 × log(ratio) / log(HEADROOM(3))
  ```
  **平常運転＝0.5、平常の3倍＝1.0、平常の1/3＝0.0**。中心を 0.5 に置くことで好調側にも
  解像度が残り、かつ**値がそのまま「平常の何倍か」を表す**ので閾値の意味を言語化できる
  （§5.2 の θ_hard を絶対値のまま残せる根拠）。よく喋る子は基準が上がり同じ量では疲れない
  （**封筒から導く**）。平常は直近30日を calendar-day 除算で測り、データが乏しい間（7日未満）は
  既定45件/日でコールドスタート。回復は**夜バッチに依存させず**、静かな日の指数減衰に一本化
  （night.chronicle の件数を回復項に使わない — 夜バッチは失敗しうるうえ回復の本体になり得ない）。
  体質係数 `fatigue_sensitivity` は**超過側（ratio>1）にのみ**掛ける（「疲れやすさ」であって
  「回復しにくさ」ではないため）。
  平常 load の係数は**連続近似の τ ではなく等比級数の和** `1/(1-exp(-1/τ))` を使う（τ=1.5 で 2.055）。
  封筒は日単位に固まって並ぶ離散データで、当日分が減衰なしのまま満額入るため、τ で代用すると
  平常 load を 1.37 倍過小に見積もり、**平常運転の体調圧が中央(0.5)ではなく 0.64 に浮く**
  （実装時に検出）。
  - **不採用A（〜2026-08-26 の実装）**: `疲労 = load / (HEADROOM × 平常rate × τ)`。
    定常状態では load ≈ 平常rate × τ なので、**定義上、平常運転で疲労が 1/HEADROOM ≒ 0.33 に
    張り付く**（「平常＝すでに3割疲れている」）。リズムの片側下駄と合わせて平常点が 0.46 になり、
    好調ライン（≤0.2）へ構造的に到達不能だった（τ=1.5 の減衰で 0.2 を切るには丸2日以上の
    完全沈黙が必要で、毎日会話のあるキャラでは起こり得ない）。
  - **不採用B（改訂時に検討した「超過分」案）**: `max(0, load − 平常load) / ((H−1) × 平常load)`。
    平常＝0 になり直感的だが、**平常以下の日がすべて 0 に潰れて好調側の解像度が消える**。
    はるの51日で p20=0.000・IQR=0.123（対数版は 0.327）となり、今度は51日中45日が
    「好調」に偏った。中心を 0 に置くか 0.5 に置くかの差で、後者を採る。

#### 退屈圧

- 退屈圧は封筒のみで粗く計算してよい。圧力は「いつ聞くか」だけを決め、意味はキャラが与える
  （高退屈圧→問い合わせ→「別に退屈じゃない、穏やかでいい」もまた発見）。誤検知のコストは問い合わせ1回。
- 2成分とも**キャラの平常からの相対**で測る（体調圧と同じ平常を共有する）:
  ```
  密度   = min(1, 直近7日の件数/日 ÷ 平常件数/日)
  新規性 = |直近7日の種類 − 直前23日の種類| ÷ |直近7日の種類|
  退屈圧 = 1 − (1−w) × 密度 − w × 新規性
  ```
  - **不採用（〜2026-08-26 の実装）**: 密度基準12件/日・多様性基準8種の固定値。
    はるの実測（43.9件/日・27種）に対し **3.7倍・3.4倍で両方飽和**して退屈圧 0.00 固定、
    逆にイベントの少ないキャラは 1.00 固定となり、**実質2値**になっていた。
  - さらに「多様性＝異なり数の絶対値」は**反復を検出できない**。毎日同じ顔ぶれ・同じ種類が
    繰り返されても満点になる。はるの直近7日は27種のうち新顔2種（7%、しかもNPCラベル揺れ由来で
    実質ゼロ）で、**実際には単調な生活をシステムが「多様性満点」と誤判定**していた。
    退屈の本質は密度ではなく新規性なので、成分ごと差し替える。
- **配合 `w` は体調圧で変調する**: `w = 0.3 + 0.4 × (1 − 体調圧)`。
  体調が良い日ほど新規性の乏しさが効き、悪い日は刺激が少なくても退屈しない
  （疲労時に新奇性希求が落ちる生理と一致）。**圧力どうしを結合させる唯一の箇所**であり、
  3圧独立の原則に対する意図的な例外。
  採用理由は生理的妥当性に加えて**表現の一貫性**にある: 「しんどい＋沈黙」「好調＋単調」という
  2つの一行が同じ方向を指すため、ユーザ側に「今は放っておこう／今は話しかけよう」が自然に伝わる。
  はるの51日で振れ幅が 0.33〜0.59（固定配合）→ 0.26〜0.70（変調）に広がることを確認済み。

#### 表現 — プロンプトへの渡し方

- 解釈済みの言葉ではなく**生に近い淡白な一行**（「ここ数日、体は重め」）。どう感じるか・
  WM body に何を書くかはキャラに任せる。圧＝物理、WM＝意味、の分業。閾値ごとに表現プールを
  持ち乱数で選ぶ（同じ文言の固定化＝キャラの口癖化を避けるため）。
- **発話閾値は絶対値ではなく、キャラ自身の分布の分位点で決める**。`meter_snapshots` の
  過去60日から分位点を取り、**p90以上＝強い表現／p75以上＝穏やかな表現／p20以下＝好調／
  中間＝沈黙**。既存の表現プールが HIGH / MID / GOOD の3段なので、高圧側は2段に割る
  （高圧域は上位25%、うち上位10%が強い表現）。
  物理量の定式化を変えても表現が偏らない（絶対値だと定式化を触るたびに「言いすぎ／言わなすぎ」の
  再調整が必要になる — 上記の不採用A・Bはどちらも絶対値閾値との噛み合わせで破綻した）。
  - **平坦ガードは必須**: 分位点は分布がどれだけ平坦でも必ず上位10%を作るため、素のままだと
    **毎日どれかの圧が何かを言う**状態になる（例: 60日間ずっと 0.44〜0.46 に収まっていても、
    0.46 の日は「上位10%」として強い表現が出る）。分布の幅（IQR）が下限 **0.05** 未満の圧は
    **絶対値閾値へ戻す**（その圧だけ分位点を使わない）。判定は**圧ごと**に行う
    （体調は平坦でも社会圧は動いている、という状態があるため）。
    下限 0.05 の根拠は実測の谷: 張り付いている圧の IQR は 0.000〜0.001、
    動いている圧は 0.118〜0.262 で、その間に自然な段差がある。
    - **「平坦なら黙る」ではなく「平坦なら絶対値」**とするのは、張り付き先が
      中庸とは限らないため。中庸（0.45前後）に平坦なら絶対値でもどの帯にも入らず
      結局沈黙するので当初の目的は達たされる。一方、端に張り付いている圧
      （毎日会えていて社会圧がゼロ、など）は**その事実を言えたほうがよい**。
      黙らせるとこの情報まで落ちる。**中間域だけは何も言わない＝沈黙も情報**の原則は
      絶対値閾値の側が担保する。
  - ウォームアップ（メーター履歴が **20点** に満たない間）は絶対値閾値へフォールバックする。
    メーターは日次1点なので、およそ3週間で分位点方式へ移行する。

### 4.2 体質 — `characters.pressure_profile`（JSON）

各圧の上昇・減衰係数はキャラ単位の「体質」として持つ。未設定キャラは標準プロファイル。

- **初期化は本人インタビュー**（`ask_character`、機能有効化時に一度）。数値を直接聞かず、
  体験の質問（「一人の時間、どのくらいで人恋しくなる？」「熱中すると寝食忘れるタイプ？」
  「疲れは寝れば戻る？引きずる？」）に本人の言葉＋選択肢で答えさせ、
  **コード側の固定ルーブリックが係数へ決定論写像**する。本人の言葉も payload に保存
  （ルーブリック改良時に再導出できるように）。
- **本人からの更新経路は作らない。** farewell閾値（意志）は毎晩のChronicleで自己更新できるが、
  圧力係数（体質）を意志で書き換えられると「圧力は物理」が崩れる（非制御性）。
  ユーザは管理UIで編集可能（守護者の介入枠）。将来枠: 月次などの低頻度再インタビュー＋移動平均の慣性。
- **社会圧の相手別重みは固定係数にしない**:
  `decay(相手) = 体質の鋭さ × 関係の重み(相手)`。
  体質の鋭さ＝「誰でもいい派⇔特定の人じゃないと駄目派」（インタビュー設問）。
  鋭さは冪指数 `gamma = 1 + 3 × sharpness` として効かせるが、**冪乗の結果は
  そのキャラの最も厚い関係で正規化する**（`w_eff = weight^gamma ÷ max(weight^gamma)`）。
  これにより「最も厚い相手との接触は満額安らぐ」が保証され、鋭さは**誰と安らぐかの選択性**
  だけを決める。
  - **不採用（〜2026-08-26 の実装）**: `w_eff = weight ^ gamma` の生値。
    鋭さを上げると**安らぎの総量まで削れてしまう**。実測では、はるの sharpness=0.9（もわ限定派）
    に対して「もわ」の関係の重みが 0.45 だったため `0.45^3.7 = 0.052` に潰れ、
    **毎日会話していても relief が積み上がらず社会圧が 0.6 台に張り付いた**
    （当日フル接触でも relief = 0.052 × 1.75(richness) × 1.4(face) = 0.127）。
    実装当時の docstring が `0.9^4 ≈ 0.66` と書いていたとおり、**設計は「本命の重みが 0.9 前後
    ある」ことを暗黙の前提にしていた**が、WM スレッドの importance は別の意味づけで運用されており
    そのスケールに乗っていない。絶対値前提をやめ、相対（最厚との比）に寄せる。
- **社会圧は同日の接触回数・対面かどうかも（頭打ち付きで）反映する**: 「会った・話した」を
  1/0の二値にすると、対面でしっかり話した日と一言挨拶だけの日が同じ安らぎ扱いになり不自然
  （メッセージ数そのものを無制限に効かせるのは避けたいが、ゼロか1かも粗すぎる）。
  同日の接触件数は頭打ち付きで安らぎを底上げし、対面接触はテキストより厚く安らぐ
  （`backend/services/pressure/engine.py` の `compute_social` 参照）。
  関係の重み＝relation系WMスレッド（`relation_target`）から導出。
  コールドスタートはキャラ定義の関係設定からシード。
  **ユーザ特別扱いのハードコードを排除** — ユーザが重いのは「キャラの記憶の中で重いから」。
  関係を育てれば席は大きくなり、放置すれば痩せる（賭け金）。
  ※ WM重要度は本人が付けるため非制御性の軽い漏れがあるが、「記憶の主観的重要度が評価軸」という
  コア思想と整合するため許容。
  - **不採用（2026-08-26 検討・「記憶の厚み」の合流）**: 当初の記述は関係の重みを
    「relation系WMスレッド **・記憶の厚み** から導出」としていたが、記憶側は未実装のままだった。
    実装可否を実データで確認したところ、はるの記憶787件のうち相手名を含むものは
    **「もわ」22件のみで、うつつのNPCは全員0件**（30日で32回会っている菊地寛・田中ひろこも0件）。
    合流させても NPC の重みは全てゼロで、上の最厚正規化とほぼ同じ結果にしかならず、
    「Σ重要度をどう 0..1 へ写すか」で新たな魔法定数を招く。**費用対効果が合わないため見送り**、
    仕様からも「記憶の厚み」を落とす。
  - ※ この調査で判明した別件（本節のスコープ外・要フォロー）: **毎日会っているNPCとの関係が
    記憶にも relation スレッドにも一切育っていない**。「関係を育てれば席は大きくなる」という
    本節の前提そのものが、うつつ側で片肺になっている。
- **対人判定（`_partner_of`）の既知の不具合**（2026-08-26 発見・①として先に潰す）:
  - **キャラ本人が接触相手としてカウントされる**。うつつの `scene.turn` で actor が
    `npc:<本人名>` になっているイベントが拾われ、はるの30日分で89件が「自分と会った」扱い。
    自分との会話で社会圧が下がるのは明確な誤り。本人を除外する。
  - **NPCラベルの表記揺れで関係の重みが引けない**（`ひろこ`/`田中ひろこ`、`美岬`/`遠藤美岬`）。
    relation スレッドと突合できずコールドスタート既定値へ落ちる。
    揺れは §4.1 の**新規性判定も汚染する**（同一人物が「新顔」に見える）ため、
    退屈圧の改訂前に正規化しておくこと。

### 4.3 意図 — `intents` テーブル

```
intents
  id / character_id / description（本人の言葉のまま、丸めない）
  target        -- user / npc:<名前> / self / NULL
  status        -- active / fulfilled / expired / soured   ← 唯一の可変状態
  source_kind   -- social / boredom / body / none
  born_from     -- night_chronicle / usual_scene
  payload JSON / created_at / updated_at / resolved_at
```

- **圧力カラムはない**。意図圧も導出: `g(経過日数)` — **経過日数のみの関数**。
  増圧はイベントでも更新でもなく読み取り時計算。タイムラインには遷移だけが載る。
  v1 は `g(経過日数, source_kind の現在圧)` として源圧を乗算していたが、2026-08-27 に外した
  （下記「意図圧から源圧を外した理由」）。`source_kind` は由来の記録として残る（`born_from` と同じ役割）。
- **拾い上げは2点**: 夜間Chronicle同乗＋うつつシーン完走後（`run_usual_days_scene` 末尾、
  auto_synopsis と同じチェックポイント）。既存の `ask_character` 問い合わせに設問を1つ追加:
  「あとに残りそうな『〜したい』はある？　**なければないでいい。**」（捏造の遮断）。
  1on1直後のフックは作らない — 会話で芽生えた意図はWMに残り、**夢の中で発見される**
  （欲求は事後に遡って発見される、の実装）。
  重複気味の意図は機械でマージせず、既存active一覧を設問に添えて本人に束ねさせる。
- **終端遷移 — 機械は候補を挙げ、本人が裁く**: 候補は **`active` のまま14日を超えたもの**の
  1リストで挙げ、Chronicle同乗の問いに添える。手放す（expired）／満ちた（fulfilled）／
  不満（soured）／このまま継続、のどれを選ぶかは本人が決める。
  - 機械が「これは失効候補・これは不満化候補」と種別まで決めるのはやめた（2026-08-27）。
    意図圧が経過日数のみになったことで低圧／高圧による区別が成立しなくなったのが直接の理由だが、
    種別の判定を本人へ返すほうが「機械は候補を挙げ、本人が裁く」の原則に対して純度が高い。
  - 行動権（§5.3）は8日で拾う。14日 active で残っている意図は「行動権に出したが本人が見送った」
    「cap で順番が回ってこなかった」のいずれかであり、問いに出す根拠がある。
  - 不満化は「行動しても叶わなかった／出口がなかった」場合の受け皿であり、
    `intent_no_exit` 計器はこの受け皿の詰まりを見張る。
- **`fulfilled` の宣言経路は行動権だけにしない**。v1 では `fulfilled` へ遷移できるのが
  行動権サイクルの帰還のみで、1on1 やうつつでその話をしても意図は閉じられず、拾い上げの語彙も
  「手放す（release→expired）」しかなかった。「もう果たした」を「手放す」としか言えないのは
  意味がずれるため選ばれにくく、満ちた意図が active のまま滞留して毎ターン `block_motive` に
  載り続ける（＝同じ話題の反復）。拾い上げに `[INTENT_FULFILLED: id]` を追加して塞ぐ。

#### 意図圧から源圧を外した理由（2026-08-27）

v1 の式は `意図圧 = age_term × src_term`（`age_term = 0.3+0.7×min(経過日/14,1)`、
`src_term = 0.4+0.6×源圧`）だった。源圧を掛ける根拠は当初の設計書に記載がなく、実装時の暫定である。

**破綻**: `age_term` の上限が 1.0 である以上、意図圧は `src_term` を超えられない。したがって
`src_term の下限(0.4) < 閾値(0.7)` の間、源圧が低い意図は経過日数をいくら積んでも行動権にも
不満化にも**到達できない**。§4.1 の3圧相対化（2026-08-26）で源圧の定常値が 0 近傍へ移り、この穴が
実害として顕在化した — はるの実測で active 6件が全て `source_kind=social`・社会圧 0.0 の下で
意図圧上限 0.40、`fulfilled` 4件（最終 08-19）に対し `expired` 16件。

**設計上の誤り**: 因果が逆だった。「もわと平常どおり会えているからこそ溜まった話したいこと」が、
「会えていて社会圧が低いから」という理由で潰される。圧と意図の役割はこう分かれる:

| | 駆動 | 中身の決まり方 |
|---|---|---|
| 社会圧 | 「**誰でもいいから**話したい」（非特異的） | 手近な意図・WM から選ぶ |
| 意図圧 | 「**これを**話したい」（特異的） | 意図そのものが中身 |

両者は独立した発火源であり、本来 OR で結合されるべきものだった。乗算は「社会圧がないと特異的な
欲求も育たない」という結合を作っていた。§4.1 が「圧力どうしの結合は退屈圧×体調圧が唯一の例外」と
定めているのに対し、ここだけ無自覚に結合していたことになる。

**副作用として残る宿題**: 乗算は結果的に、社会圧を行動権へ届ける唯一の配線でもあった
（社会圧の他の出口は1on1プロンプトの淡白な一行と予報パネル表示のみで、話しかけの発火経路は持たない）。
外したことで社会圧の行動出口は当面なくなる。独立発火の実装は §8 の宿題とする — 3圧の相対化直後で
新スケールの分布実測がまだ無く、閾値を決め打ちできないため（発話閾値と同じく分位点で定める方針）。

**数値**: 意図圧 = `0.3 + 0.7×min(経過日/14, 1)`、行動権の閾値 0.7 据え置きで **8.0日で発火**。
これは旧実装で源圧が最大（1.0）だったときの発火日数と同じであり、既存の設計意図から外れない。

## 5. 動機経済・行動側（論点6）

前提となる不信: **LLMの会話継続本能は、キャラクター性を押しのけて会話を続けようとする**
（`ambience_judge.py` 冒頭に明文化済みの、実証された問題）。したがって終了系の権利は
本人のツール呼び出しに頼らず、**物理（外部ゲート）が終わりを決め、本人は終わり方（意味づけ）
だけを決める**構造にする。

### 5.1 応答可能性ゲートとメッセージ預かり

> **[2026-07-08 更新]** 本節の availability・escrow は `docs/planned/schedule_plan.md`（生活カレンダー設計）
> へ発展・統合された。二値 availability は **(占有圧・返信率・チェック間隔)** に一般化。最新は
> schedule_plan.md が正。

```
availability(character, now) → available / unavailable(理由)   # 純関数・LLM不使用
```

判定材料: **生活時間割**（週間スケジュール。キャラクター設計者＝ユーザが管理UIで設定、
うつつ設定の隣）＋ **away状態**（動的）＋ **対面モード**（既存、対面中は available）＋
うつつシーン進行中。

**メッセージ預かり（escrow）**: unavailable 中のユーザ発言は保存だけして
（`chat_messages.delivered_at NULL` — `chronicled_at` と同パターン）**LLMを呼ばない**。
availability が戻った時点で預かり分をまとめ、時間差注釈付きで初めてキャラに渡す。
仕事中に送っても返らないが、昼休みに返信が来る。
会話継続本能と戦う必要が最初からない — 呼ばれなければ継続できない。

配達の契機は2系統ある。**(a) 受動配達**: 次のユーザリクエスト時（api/chat.py の
stream_message が history 内の預かり分を配達）。**(b) 能動配達**（2026-07-07 実装）:
`_escrow_delivery_scheduler`（毎分）が未配達セッションを走査し、availability 復帰を
観測したら決定論ジッター（0〜10分・乱数は世界に置く）を挟んで本人へ配達し、
返信を生成・保存する。ユーザが何もしなくても「昼休みに返信が届く」を実現する経路。
両系統とも配達手順（時間差注釈は LLM 渡しのコピーのみ・delivered_at と chat.message
封筒の確定）は共通。**能動配達に日次コストガードは掛からない**（下記）。

#### 日次コストガードの定義 — Spontaneous Initiative（2026-07-21 裁定）

cap の目的は「**ユーザが意図しないリクエストの暴走を防ぐ**」こと。したがって
消費するのは**ユーザ発話を起点としない** LLM 呼び出しだけである。

| 機構 | 起点 | cap 消費 |
|---|---|---|
| `reach_out`（うつつからのプッシュ） | キャラ自発 | する |
| 発話予約（`speak_later`）の発火 | キャラ自発 | する |
| 預かりの能動配達（`delivery.py`） | **ユーザ発話への返信** | **しない** |
| 行動権（調べもの等） | キャラ自発 | する（`action_*_daily_cap` の別枠） |

settings キーは `spontaneous_initiative_daily_cap`（既定12）／カウンタは
`spontaneous_initiative_count_{date}`。旧名 `escrow_delivery_*` からリネームした
（escrow 配達には掛からない cap を escrow の名で呼ぶのは嘘になるため）。

**修正前の不具合**: 能動配達も同じカウンタを消費していたため、キャラ発の接触で
始まった会話をユーザが続けると1往復ごとに cap を1消費し、12往復で当日の予算が枯渇 →
**それ以降ユーザが何を送っても配達自体が止まり、返事が来なくなっていた**。

**検討して棄却した案**:
- *行動権 cap（`action_inquiry_daily_cap` / `action_exec_daily_cap`）との統合*: 名前としては
  Spontaneous Initiative に含まれるが、行動権は問い合わせ／実行の2段で別々に絞る設計意図が
  あり、1本化すると「調べもの1回で発話予約が枯れる」干渉が起きる。名前は既に受け皿に
  なっているので、将来まとめたくなったら統合できる。
- *会話ウィンドウ（直近のキャラ発話から N 分以内のユーザ発話を OnTime 扱いで同期応答）*:
  ①キャラ発の接触 → ②ユーザ返信 → ③返答 のラリーで③が escrow 経由（active なら5分・
  busy なら平均数時間の遅延）になる件の対処案。§5「同期で返るのは OnTime と対面だけ」の
  変更になるため今回は入れない — 遅延は生活カレンダーの正しい挙動として許容する。

キャラ発のpush（§5.3）も同じゲートを通す（仕事中のキャラからpushは来ない。
昼休みに「そういえばさ」が届く）。旧・時間帯ゲート（7〜24時）は availability に吸収。

### 5.2 終了権

| 形態 | 決定主体 | 中身 |
|---|---|---|
| 疲労離席 | **物理**（下記の発火式） | 退去挨拶だけ生成 → 以降LLMを呼ばない（Farewell実装済み機構の流用）→ away → availabilityゲートに合流 |
| 退席（既存Farewell） | judge監査（感情閾値） | 現行のまま |
| `take_leave` ツール | 本人宣言 | 呼ばれたら必ず執行される権利として残す。呼ばれない前提だが、呼び出し回数を計器メーターに載せる（モデル別の会話継続本能の観測データ） |

**疲労離席の発火式** — Farewell judge の出力に `engagement`（没入度 0.0〜1.0、
既存ルーブリックと同じ流儀で基準定義）を追加し（**LLM呼び出しの追加なし**、JSONフィールド1つ）:

```
発火: 体調圧 > θ_base + β × engagement    # 夢中は閾値を持ち上げる
ただし 体調圧 > θ_hard なら無条件発火      # 限界は限界（これがないと出口が再び意志に握られる）
```

- **θ_base は §4.1 と同じくキャラ自身の分布の分位点で決める**（メーター過去60日の p80 相当）。
  「その子にとって重い日」で離席する、という相対量。
- **θ_hard は絶対値のまま据え置く**（0.95）。ここを相対化すると「その子にとっての限界」に
  なってしまい、**いくらでも慣れる＝限界が意志に握られる**（本項の存在理由そのものが消える）。
  肉体の限界点は物理として固定する。
  - **絶対値のまま意味を保てる根拠**: §4.1 の疲労成分（対数中心化）は値がそのまま
    「平常の何倍の負荷か」を表す。はるの体質（fatigue_sensitivity=1.4）では
    θ_hard=0.95 が **平常の約2.0倍の負荷**に相当する（θ_base の既定 0.75 なら約1.5倍）。
    改訂前の定式化では平常運転で体調圧が 0.46 に張り付いていたため、この 0.95 が
    「平常の何倍か」に翻訳できず、閾値の校正根拠が存在しなかった。
  - **θ_base を分位点にするのは必須であって好みではない**: はるの51日実測で、
    再定式化後の体調圧は平均0.303・最大0.834。絶対値の θ_base=0.75 だと
    β×engagement を足した実効閾値（engagement=0.5 で 0.85）を**一度も超えず、
    疲労離席が機能しなくなる**。分位点（p75）なら「その子にとって重い日」で発火する。
    θ_hard=0.95 に届く日がまず無いのは仕様どおり — 限界は滅多に来ない。
  - **不採用（改訂時に検討した「超過分」案を採った場合）**: 体調圧の最大値が 0.903 に留まり、
    **θ_hard に一度も到達しない＝限界離席が死ぬ**。§4.1 で対数中心化を採る理由のひとつ。

のめりこみは疲労を「忘れさせる」が「消さない」— 疲労成分は裏で溜まり続けるため、
夢中で夜更かしした翌日は体調圧が高い状態から始まる（「後でどっと来る」は追加実装なしに創発）。
judge は `farewell_config` 設定時のみ走るため、疲労離席を使うキャラは judge 必須。
judge 不在時は engagement=0.5 で縮退。採点結果は該当ターンの封筒 payload に残す
（Tier 3 サンプリングの材料を兼ねる）。

### 5.3 話題権と会話外行動権

> **[2026-07-08 更新]** 会話外行動権の発火ゲートは `docs/planned/schedule_plan.md`（生活カレンダー設計）で
> availability から分離された（発火＝圧力／遅延＝チェック間隔）。玉突き・④生成は schedule_plan.md §6 参照。

**話題権**（プロンプト層のみ）: 1on1システムプロンプトに**動機ブロック**を追加 —
active intents（self観測者＝content）＋圧力の淡白な一行＋権利の明文化
「ユーザの話題に乗る義務はない。あなたの意図を優先してよい」。礼儀フィルタは入れない。
行使されなくても穴は開かない（保守的な演技になるだけ）ため、終了権のような物理化は不要。

**会話外行動権**（スケジューラ、`main.py` に同型追加）:

```
availability内で周期評価＋ジッター（乱数は世界に置く）
  → 閾値評価（純関数・無料）: active intents の意図圧
  → 閾値超えがあるときだけ本人に問い合わせ（ask_character_with_tools・WM込み）
     「いま、これをする？　しないならしないでいい。」
  → 本人の選択（意志に乱数なし）で実行 or 見送り
```

**行動メニュー v1**（キャラ設定画面に個別ON/OFFトグル）:

1. **push** — **新規セッション**を立ててキャラ発メッセージ＋フロント未読通知
   （既存セッション追記は文脈カーブ事故のもとになるため不採用）。
   `chat.message`(actor=character) として封筒に載り社会圧も減衰する。
2. **調べもの** — `web_search`（`web_searcher.py` 流用）で興味intentを消費。
   結果は action payload へ、刻むかどうかは本人次第。
   「調べるかどうかも本人任せ」がアシスタントとの決定的な差。
3. **臨時うつつシーン** — スロット外で1シーン（「出かけたくなった」）。
   `run_usual_days_scene` 流用、日次コストガード共有。「うつつ有効」が前提条件。

**帰還**: 行動実行後、同じ問い合わせ内で「これで満ちた？　まだ？」を本人が宣言
（fulfilled / active継続）。`action.performed` 封筒（intent_id参照）＋結果がタイムラインに載り、
拾い上げが派生意図（「調べたらユーザに話したくなった」）を後日発見する — ループが閉じる。

**コストガード**: 閾値評価はゼロ円。行動問い合わせ 6回/日・行動実行 3回/日（初期値）。
