# シナリオ履歴窓・あらすじ上限の見直し

2026-10-15 決定・実装。

## 背景

シナリオの GM が長いセッションで過去を取りこぼす（「記憶が怪しい」）。実測では GM に渡って
いたのは「生ログ約 8000 字＋あらすじ約 2000 字」で、本文は大量にある。原因は 2 つ。

1. **履歴上限「ターン数」が話者バブル数で数えられていた。** GM の 1 レスポンスは複数の
   `@話者:` ブロック（＝`scenario_turns` の複数行）に割れるため、「100 ターン」が実質
   100 バブル（約 8000 字）で頭打ちになり、文字数上限 80000 字に届かなかった。
2. **あらすじ上限がプロンプト直書きの 2500 字前後／最大 3000 字だった。** 生ログ窓が狭い
   ため蒸留が「未蒸留 4000 字ごと」に走り、要約の要約を何十回も重ねて古い区間が痩せた。

## 採用した設計

### 1. 履歴上限のターン数をレスポンス単位で数える

- 「レスポンス」＝ 1 回の LLM 呼出で生まれたバブル群。`raw_response` が同じで連続する行を
  1 レスポンスに束ねる（フロントの `response_key` によるレスポンスグループと同じ単位）。
  `raw_response` が NULL の行（ユーザ発話・intro）は 1 行で 1 レスポンス。
- `slice_history` はレスポンス単位で直近から詰める。**レスポンスの途中で窓が切れない**
  （旧実装はレスポンスの途中から履歴が始まることがあった）。
- あらすじ自動蒸留のトリガー判定・進捗バーの「ターン」もレスポンス数で数える。
- 列名 `history_max_turns` は据え置き（意味だけレスポンス数に変わる）。既存値は全シナリオ
  NULL（既定 100）だったので値の読み替えは不要。

### 2. GM プリセットにコンテキストウィンドウ長を持たせ、シナリオ側で振り分ける

- `llm_model_presets.context_window_tokens`（NULL 可）を新設。モデルプリセット画面で設定。
  モデル本来の最大値でなく「このプリセットで使ってよい長さ」として入れてよい（コスト調整のノブ）。
- シナリオ側の振り分け: 履歴に使う総量 ＝ コンテキスト長 × 1/2（残りはシステムプロンプト・
  シナリオ本文・出力・思考の余白）。総量を **生ログ 6：あらすじ 4** に割る。
  日本語は 1 トークン ≒ 1 文字と見なしてトークン数をそのまま文字数に読み替える（概算）。
  例: 200,000 トークン → 総量 100,000 字 → 生ログ 60,000 字・あらすじ 40,000 字。
- 定数は `context.py` の `HISTORY_SHARE_OF_CONTEXT`（1/2）/ `RAW_LOG_SHARE`（6/10）と
  `synopsis.py` の `SYNOPSIS_TO_HISTORY_RATIO`（4/6 ＝ あらすじ / 生ログ）。
- 解決順: GM プリセットの `context_window_tokens` から算出 → 設定
  `scenario_chat_default_history_max_chars`（生ログ文字数）→ 80000。
- GM プリセットはセッション単位（`scenario_sessions.gm_preset_id`）なので、同じシナリオでも
  モデルごとに読める量を変えられる。うつつは `ensure_usual_session` が記録した GM プリセット。
- あらすじ蒸留に別プリセット（`synopsis_preset_id`）を使っていても、基準は **GM プリセット**
  （あらすじを読むのは GM のため）。
- `scenarios.history_max_chars` は廃止（DROP COLUMN）。シナリオ編集・うつつ欄の入力も撤去。
- 当初はプリセットに生ログ文字数そのもの（`history_budget_chars`）を持たせたが、同日中に
  「プリセットはモデルの性質（コンテキスト長）、振り分けはシナリオの都合」と分けるため
  `context_window_tokens` へ置き換えた（旧列は DROP。値は未設定だったので移行なし）。

### 3. あらすじ上限 = 生ログ上限 × 4/6（ラチェット付き）

- 生ログ：あらすじ ＝ 6：4。`synopsis_cap = max(生ログ上限 × 4/6, 既存あらすじの長さ)`。
- プロンプトは「最大 N 字を超えない」。旧来の「2500 字前後」のような目標値は置かない
  （上限が大きいとき、目標値があると水増しを誘うため）。
- **圧縮は上限に収めるための手段であって目的ではない**、と位置づける。上限に余裕があるうちは
  台詞・固有名詞・やりとりの経緯を省略・要約せず具体的に残し、足りなくなったら古い経緯から
  順に畳む（そのときの省略・要約は歓迎）。旧プロンプトは 3000 字上限時代の「簡潔な箇条書き」
  「古い経緯は 1〜2 行に畳んでよい」を無条件に出しており、上限 20 万字・材料 18 万字でも
  3717 字（約 1/49）まで潰し、余裕があるのに台詞を「…」で省略していた（2026-10-15 実測）。
- **ラチェット**: 小さい窓のモデルへ切り替えても、既存あらすじの長さを下回る上限にはしない。
  あらすじは上書き保存で前世代を残さないため、上限を縮めた蒸留は不可逆に情報を失う
  （大きいモデルへ戻しても復元できない）。
  - 代償: 一度広がった上限は自動では戻らない。縮めたいときはユーザが UI であらすじを手で削る。
  - モデルが上限をわずかに超過すると、次回上限がその分だけ広がる（漂流）。許容する。

## 検討して棄却した案

- **比率 7:3**: 1 回の蒸留の圧縮率が約 2.2 倍。6:4（約 1.9 倍）を試すことにした。
  比率は 1 か所の定数（`SYNOPSIS_TO_HISTORY_RATIO`）なので後から調整できる。
- **シナリオ側 `history_max_chars` をシナリオ単位の上書き用に残す**: 手軽さを優先して廃止。
  結果としてモデルの予算いっぱいまで生ログを使うが、トレードオフとして受け入れる。
- **あらすじの目標文字数・下限を数値で示す**（例: 材料の総量 × 1/5）: 圧縮指示を緩めれば
  足りると判断。数値目標は水増しを誘う懸念もある。
- **プリセットに生ログ文字数を直接持たせる**（初版の `history_budget_chars`）: プリセットに
  シナリオ固有の振り分け結果が混ざり、比率を変えるたびに全プリセットを入れ直すことになる。
  プリセットはコンテキスト長だけを持ち、振り分けはシナリオ側の定数で行う形にした。
- **プリセットのコンテキスト長を API から自動取得する**: Anthropic の Models API
  （`max_input_tokens`）、Gemini の `inputTokenLimit` などで取れるものはあるが、手元のモデルは
  軒並み 1M 前後で、律速はコンテキスト長ではなくコスト・レートリミット・注意の質。
  モデル本来の最大値をそのまま使うと意味のある値にならないため、手入力とした。
  claude_cli プリセット（`opus` 等のエイリアス）は API で引けない点もある。
- **あらすじ上限を毎回生ログ上限から素直に計算（ラチェットなし）**: 大→小のモデル切替で
  あらすじが不可逆に縮む事故があるため棄却。
- **生ログを「蒸留済み境界より後ろだけ」送る（キャッシュ向け）**: スライド窓は上限到達後
  毎ターン先頭がずれてプロンプトキャッシュが効かない。蒸留時に一括で切り落とせば蒸留間は
  追記のみになりキャッシュが効くが、GM の主力が claude_cli（キャッシュ無効）であり、
  別の改修として今回は見送り。
