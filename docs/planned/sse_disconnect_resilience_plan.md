# SSE 切断耐性 — 応答を接続の生死から切り離す

対象: 1on1（`api/chat.py`）／シナリオ（`api/scenario_chat/stream.py`）の SSE ストリーム。
状態: 実装済み（2026-08-05）。

## 発端 — 観測された事故

`debug_log_entries.request_id = c799f37d`（2026-08-05 13:33:53、シナリオ）で、
**LLM は完走したのに応答が DB に一行も残らなかった。**

| 時刻 | 出来事 |
|---|---|
| 13:33:53 | シナリオ stream 受付。ユーザ発話 turn 595 は保存済み |
| 13:34:35 | Claude CLI は正常完走（`subtype: success` / 2146 out tok / $0.15 課金済み） |
| — | `scenario_turns` に GM 応答が 0 件。`debug_log_entries.response` も NULL |

同型の事故が同日 13:18〜13:19 にもあり、そちらは**シナリオと 1on1 が同時に落ちている**
（`9f294591` = CLI 完走・保存ゼロ、`e565ad8f` = FrontInput しか残っていない）。

コンソールに traceback は無し。`logs/chotgor.log` にも記録は無い
（`uvicorn.error` は root へ propagate しないため、ASGI 例外は**そもそもファイルログに出ない**。
全期間で `Traceback` 0 件なのはそのせい）。つまりサーバ例外ではなく**クライアント切断**。

### なぜ消えるのか（構造）

生成の永続化が SSE 接続の生存に依存していた。

- シナリオ: `_run_gm_turn` は `engine.generate_stream` の chunk を `yield` しながら進み、
  **ストリームを流し終えてから `_save_turn` を呼ぶ**（`services/scenario_chat/service.py`）。
- 1on1: `sse_generator` も同様に、ループ完了後に `create_chat_message` でキャラ発話を保存する
  （`api/chat.py`）。

クライアントが切れると Starlette がジェネレータをキャンセルし、保存コードに到達しない。
一方 `claude_cli` プロバイダは daemon スレッドで CLI を読み続けるため、生ログと課金だけが残る
（観測された痕跡と一致）。**課金だけされて応答が消える**のが実害。

### なぜ切れたのか（誘因）

`claude_cli` は `assistant` イベント（＝ブロック完成時）でしか chunk を出さないため、
`c799f37d` は接続確立から 42 秒間 SSE に 1 バイトも流れていない。
同時刻の 1on1（73 秒）は生き残っているので、タブ全体のリロードではなく
**その接続だけが沈黙で切られた**と見るのが自然（モバイル回線・中間装置の無通信タイムアウト）。

## 採用した対策

### A. 生成を接続から切り離す（本命）

生成本体を `asyncio.create_task` で独立タスクにし、SSE 送出側は `asyncio.Queue` を読むだけにする。
クライアントが切れてもタスクはキャンセルせず完走させる → 保存は必ず行われる。

### E. heartbeat

キューが空のまま既定秒（15s）経ったら `: ping\n\n`（SSE コメント行）を流す。
沈黙で切られる確率そのものを下げる予防線。フロントの `parseSSEStream` は
`data: ` で始まらない行を読み飛ばすため、パーサ側の改修は不要。

### C. 切断の記録

切断を検知したら warn ログ＋`debug_logger.log_warning("sse_disconnect", ...)` を残す。
これまでは「消えた事実」すら記録に残らなかった。A が入った後も、
E の効果（まだ切れているか）を測る計器として機能する。

### 共通化

上記 3 点はシナリオと 1on1 で骨格が完全に相似のため、`lib/sse_runner.py` に集約し
両者から使う。切断まわりの挙動が 1 箇所に集まり、今後のストリームにも同じ保証が乗る。

## 検討したが採用しなかった案

- **保存を `yield` の前に寄せるだけ（最小修正）**
  キャンセルは `await` 中に飛んでくるので、ストリーム途中で切れたケースを救えない。
  応急処置にしかならず、A を入れるなら不要。
- **`asyncio.shield` で保存区間を守る**
  シールドできるのは個別の await であって、非同期ジェネレータ全体の巻き戻しは止められない。
  保存が「ジェネレータの内側」にある限り解決しない。
- **切断時に生成タスクを cancel する（リソース節約）**
  切断の主因がモバイルの一時切断である以上、cancel は「戻ってきたら消えている」を再生産する。
  完走させてこそ A の意味がある。LLM 呼び出しは既に始まって課金も確定しているので、
  途中で殺しても得はない。
- **SSE の再接続（Last-Event-ID による再開）**
  ストリームの途中から再開するには、イベント列をサーバ側に保持する必要があり
  実装コストが跳ね上がる。保存さえ守れば「再取得すれば続きがある」で足りる。

## 残課題

- **フロント側の自動復帰（D）**: 現在は切断されると `setError` で終わる。サーバ側が
  完走・保存するようになったので、`done` を受け取らずにストリームが終わった場合に
  ターン／メッセージを再取得すれば「戻ってきたら続きがある」になる。
  シナリオ側は `handleScenarioSend` が完了後に `fetchScenarioTurns` を呼ぶが、
  切断直後はまだサーバ側タスクが走っている最中なので空振りする（遅延リトライが要る）。
- **`uvicorn.error` がファイルログに出ない**: 今回の切り分けでコンソールを見に行く必要が
  あった。`setup_logging` で `uvicorn.error` を root へ流すかどうかは別途判断。
- **SQLite の同時書き込み**: `create_engine` は WAL も `busy_timeout` も未設定。
  今回の原因ではなかったが、うつつ・1on1・シナリオが同時に書きにいく構成である以上、
  ロック競合は潜在的なリスクとして残る。
