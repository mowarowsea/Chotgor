# テキスト添付 仕様書 — ファイルを読ませる

## 概要

1on1 チャットの添付に **テキストファイル**（`.txt` / `.md` / ソースコード / CSV / JSON など）を
加える。画像・音声と同じ添付の仕組み（`chat_attachments`・最新ターンのみ・痕跡テキスト）に
そのまま乗せ、種別 `text` として扱う。

前提となる添付の汎用化（画像専用 → 種別付き）は `docs/planned/audio_attachment_plan.md` で
済んでいるため、ここでは差分だけを書く。

## 要件（2026-10-06 合意）

1. 添付ボタンからテキストファイルを選んで渡せる
2. 中身は本文テキストとしてキャラクターへ届く（**全プロバイダー対応**。テキストなのでモデル能力に依存しない）
3. 寿命は画像・音声と同じ **最新ターンのみ**。過去ターンは痕跡テキストへ落とす
4. ファイル名もキャラクターへ届く（「さっきの README」と言えるように）

## 設計

### 種別判定 — MIME ＋拡張子

`lib/attachments.attachment_kind` に `"text"` を足す。判定は MIME が `text/*`、または
テキスト系の `application/*`（`json` / `xml` / `yaml` / `toml` / `javascript` 等）。

ただしブラウザ（特に Windows）は `.md` を空 MIME、`.csv` を `application/vnd.ms-excel`、
`.ts` を `video/mp2t` で送ってくるなど MIME が当てにならない。そこでアップロード時に
`resolve_upload_mime(content_type, filename)` で **MIME から種別が出ず、拡張子がテキスト系
なら `text/plain` に正規化して保存** する。以後の判定は保存済み MIME だけで完結し、
「種別は mime から導出」の原則を崩さない。

### データ — `chat_attachments.filename` を追加

ファイル名は中身の一部（キャラクターに見せる・UI に出す）なので、nullable 列
`filename` を追加する。既存行（画像・音声）は NULL のまま。マイグレーションは
`_migrate_add_attachment_filename`（ADD COLUMN のみ・冪等）。

### サイズ上限

テキストは丸ごとプロンプトに載るため、**1 MB を超えるテキストはアップロード時に 400** で弾く
（誤って巨大ログを渡してコンテキストとトークンを溶かす事故の防止）。画像・音声は従来どおり無制限。

### 内部メッセージ表現

最新ターンでは `build_message_content` が OpenAI 準拠の text パートを足す:

```
{"type": "text", "text": "\n\n<file name=\"README.md\">\n…中身…\n</file>"}
```

- 独自パート型を作らない。text パートは全プロバイダーがそのまま扱える
  （claude_cli / ollama はテキストパートを連結、google は Part(text)、openai 系は素通し）
- 先頭の `\n\n` は claude_cli の `_content_text`（区切りなし連結）対策
- パート順は「本文 → 添付 → ターン注釈」。claude_cli は `<turn_context>` の手前を
  ユーザ発言として `<ユーザ名>` タグで包むので、ファイルは「ユーザが渡したもの」側に入る
- 文字コードは UTF-8（BOM 可）→ CP932 の順に試し、どちらでも読めなければ置換文字で読む

### 痕跡テキスト

過去ターンでは `[テキストファイルを渡した: README.md, memo.txt]` の1行に落とす。
画像・音声は種別だけだが、テキストはファイル名が会話の参照点になるので残す。
ファイル名が無い（NULL）場合は `[テキストファイルを渡した]`。

### プロバイダー能力

`BaseLLMProvider.SUPPORTED_ATTACHMENT_KINDS` の既定を `{"image", "text"}` に、
google を `{"image", "audio", "text"}` にする。

### フロント

- `lib/attachments.ts` に `text` を追加。ファイル選択時は `File.type` に加え拡張子でも判定する
- accept 属性にテキスト系 MIME と拡張子を並べる。ボタンの title は「画像・テキストを添付」等
- 入力欄のプレビューと吹き出しの添付表示は、テキストを **ファイル名チップ**（クリックで別タブ表示）で出す
- 配信 API はテキストに `charset=utf-8` を付けて返す（日本語の文字化け防止）

## 棄却した設計案（検討記録）

- **フロントで中身を読んで本文に差し込む** — バックエンド改修ゼロで済むが、ファイルとして
  残らず、過去ターンでも全文が毎回再送される（添付の寿命の仕組みに乗らない）。棄却
- **独自パート型 `{"type": "file", ...}` を作る** — 全プロバイダーに変換を書く必要があり、
  結局テキストに落とすだけなので text パートで直接作る。棄却
- **ファイル名を持たない（種別のみ）** — マイグレーション不要になるが、キャラクターが
  何のファイルか分からず、UI でも区別がつかない。棄却
- **拡張子判定をフロントだけで行い、正規化 MIME で送る** — バックエンドが唯一の根拠という
  原則に反し、別クライアントから送るとすり抜ける。バックエンドで正規化する
- **文字コード自動判定ライブラリ（chardet 等）** — 依存を増やす割に、実用上は UTF-8 / CP932 で足りる。棄却
