# 記憶想起アルゴリズムの解説 (Memory Recall Algorithm)

現在の Chotgor における記憶想起の仕組みは、**「セマンティック検索（意味的類似性）」**と**「時間減衰を伴う重要度（鮮度と価値）」**を組み合わせたハイブリッド・スコアリング方式を採用しています。

## 0. 想起クエリの作り方 (`chat_flow/preparation.py:prepare_context`)

自動想起（pre-recall）のクエリは **「最新の user メッセージから XML タグを除去し、末尾
`RECALL_QUERY_MAX_CHARS` 文字だけを残したもの」** である。1on1・シナリオPC・うつつPC の
すべてがこの単一の合流点を通り、文脈ごとの分岐は持たない。

**なぜ末尾を残すか（先頭ではなく）**:
会話でも統合履歴でも、**いま応答すべき最新の発話は必ず末尾**にある。embedding モデル
（ruri-v3-310m 等）はモデル最大長を超えた入力を *先頭を残して* 切り捨てるため、長い
クエリをそのまま渡すと「一番古い発話」でクエリしてしまう。

**なぜ上限が必要か**:
うつつPC は `external_scenes.build_unified_pc_messages` が1日ぶんの全シーンを**単一 user
メッセージ**として渡す設計であり、クエリが数十万文字になる。infinity の入力上限
（122,880 文字）を超えると HTTP 422 → `EmbeddingError` となり、保存記憶の想起と WM heat
想起が**両方**落ちて `memory_degraded` 告知がキャラクターへ注入される。実際に 2026-07-21〜
08-06 のうつつPCターン 56 件が全滅した（原因は 422 だが、上限未満でも先頭切り捨てにより
実質無意味なクエリになっていた）。

1on1 の通常メッセージは上限を下回るため、この規則の導入による挙動変化はない。

## 1. 全体フロー (`InscribedMemoryManager.recall_inscribed_memory`)

記憶の想起は以下の4ステップで行われます。

1.  **候補抽出 (Semantic Search)**:
    *   LanceDB を使用して、クエリに対して意味的に近い記憶を `top_k * 2` 件抽出します。
    *   距離計算には `cosine` 類似度が使用されます。
2.  **重要度の時間減衰計算 (Time Decay)**:
    *   SQLite に保存されている各記憶の「4種類の重要度」と「最終アクセス時間」をもとに、現在のスコアを算出します。
3.  **ハイブリッド・リランク (Hybrid Reranking)**:
    *   `類似度スコア (50%)` + `時間減衰後の重要度スコア (50%)` の合算値で並び替えます。
4.  **アクセス情報の更新**:
    *   最終的に選ばれた `top_k` 件の記憶について、SQLite上の `last_accessed_at` を現在時刻に更新します（これにより「思い出した記憶」は鮮度が戻り、忘れにくくなります）。

## 2. 重要度と減衰のロジック ([calculate_decayed_score](file:///c:/Users/seamo/Chotgor/backend/core/memory/manager.py#16-52))

記憶の価値を以下の4つの観点で評価し、それぞれ異なる「半減期（半分に減衰する期間）」を設定しています。

| 重要度タイプ | 重み | 半減期 | 特徴 |
| :--- | :--- | :--- | :--- |
| **contextual** | 1.0 | 7日間 | 文脈的価値。短期的に重要だが、すぐに古くなる。 |
| **user** | 0.8 | 30日間 | ユーザーに関する情報。中長期的に保持される。 |
| **semantic** | 0.6 | 90日間 | 知識や概念。長期的に保持される。 |
| **identity** | 0.3 | 無限 | キャラクターのアイデンティティ。一切減衰しない。 |

**計算式:**
各重要度ごとに経過日数に応じた指数減衰 ($e^{-\lambda t}$) を計算し、重み付け合計したものが [decayed_score](file:///c:/Users/seamo/Chotgor/backend/core/memory/manager.py#16-52) となります。

## 4. 記憶ブロックの注入量と圧縮方針

想起アルゴリズムが「何を選ぶか」を決めるのに対し、この節は **選んだものを
どれだけの分量でプロンプトへ載せるか** を規定する。

### 4.1 なぜ規定が要るか（2026-08-13 の実測）

はる（運用中の主キャラ）のシステムプロンプトに載る記憶系ブロックを実測した:

| ブロック | 文字数 | 内訳 |
| :--- | ---: | :--- |
| WM スレッド一覧（71本・Close 済 44本を含む） | 7,102 | 1行あたり約100字 |
| WM 固定注入（emotion/body/relation 3本） | 762 | latest_post 200〜300字/本 |
| WM heat 想起（task/topic 5本） | 約2,360 | 1本約470字 |
| 想起記憶（identity 5 + other 5） | 2,100〜3,300 | 1件平均210字・最長409字 |
| 合計 | 約12,400〜13,600 | 日本語概算で 8〜10k token |

問題は2つある。

1. **1件あたりが伸び続けている。** WM ポストの月平均は 145字(5月) → 188(6月) →
   240(7月) → 237(8月)。長さの作法がどこにも書かれていなかったため、
   キャラクターが「丁寧に書くほど良い」方向へ自然にドリフトした。
2. **一覧ブロックが単調増加する。** Close 済みスレッドも全件が毎ターン載る構造で、
   件数の上限がなかった（月10本ペースで増える）。

肥大は文脈を圧迫し、アテンションを劣化させる。実際に「キャラクター自身の発言を
ユーザの発言と取り違える」混線が観測された。

### 4.2 書き手側の作法（キャラクターへの誘導）

Chotgor はキャラクターの記憶を直接編集しない。長さは **Chronicle プロンプトと
ツール description による誘導** で制御する。目安は以下（厳格な上限ではなく、
必要なら超えてよい旨を併記する）:

| 対象 | 目安 | 置き場所 |
| :--- | :--- | :--- |
| WM ポスト本文 | 200字 | `threader.POST_WORKING_MEMORY_THREAD_SCHEMA` / Chronicle |
| WM summary | 30字（Open/Close 共通） | 同上 |
| WM atmosphere_tag | 20字 | 同上 |
| inscribe content | 150字 | `inscriber.INSCRIBE_MEMORY_SCHEMA` / Chronicle |

**長期記憶（IM）と WM の役割分担**（長さより効く規定）:
IM は *印象・雰囲気・長期に残すエッセンス* を置く場所であり、具体的な出来事・
経緯・会話の引用は WM 側に置く。IM が「その日の日記」になっていると、
1件あたりが必然的に長くなり、かつ想起時のノイズにもなる。

### 4.3 読み手側の絞り込み（注入側の制御）

| 施策 | 実装 |
| :--- | :--- |
| Close 済みスレッドの行を短縮（`[id] (type) summary` のみ。atmosphere_tag・重要度を省く） | `request_builder._format_thread_index` |
| 一覧に載せる Close 済みを直近 N 本（既定30）に制限し、省略本数を告知する | `WorkingMemoryManager.list_all_threads(closed_limit=...)` |
| 省略分を本人が取りに行ける導線 | `read_working_memory_list` ツール |
| heat 想起の件数を 5 → 3 件、かつ heat 下限（既定 0.05）未満を切る | `WorkingMemoryManager.recall_threads` |

一覧から Close 済みを省くのは「キャラクターの視界を奪う」施策になりうるため、
**省略本数の告知行**と**取得ツール**を必ずセットにする（存在は視界に入っている、
中身は必要なときに取りに行く、という形にする）。

### 4.4 検討したが採らなかった案

- **WM ポストを「前回からの差分だけ」書かせる**: 経緯が読めないと何が新事実かを
  毎回判定させることになり、かえって A→B→A'→B' の重複記載を誘発する。
  WM は短期記憶であり、ある程度の経緯・詳細を含むこと自体は正しい。
  長さは 4.2 の目安だけで抑える。
- **固定注入・heat 想起の latest_post を表示上でトリムする（例 300字＋"…"）**:
  途中で切れた本文を見たキャラクターが `read_working_memory_thread` を
  引きやすくなり、かえってトークンを消費する。
- **一覧から Close 済みを全部落とす**: 「過去に何を越えてきたか」の連続性が
  消える。短縮行＋直近30本＋告知の組み合わせで足りる。
